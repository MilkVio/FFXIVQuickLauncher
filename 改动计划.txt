# 二、当前问题

当前新账号二维码登录大致是：

```text
先解析不到具体账号
→ 使用共享设备画像 S 生成二维码并完成扫码认证
→ 扫码成功后才知道账号 A
→ 再询问使用共享画像还是配置独立画像
→ 用户配置独立画像 P1
→ 使用二维码返回的 QuickLoginSecret 和 P1 立即再执行一次 QuickLogin
→ 保存账号
```

这个流程存在问题：

1. 第一次二维码认证已经让服务端看到“账号 A + 共享画像 S”。
2. 后面改为 P1 无法消除第一次关联。
3. 扫码完成后在后台线程创建 WPF 窗口，会触发：

```text
System.InvalidOperationException:
调用线程必须为 STA，因为许多 UI 组件都需要。
```

4. 二次 QuickLogin 只是为了把首次使用的共享画像切换为新画像；如果第一次扫码从一开始就使用最终画像，就不再需要这次立即重登。

# 三、目标流程

修改后的流程应当是：

```text
点击二维码登录
        ↓
在生成二维码前弹出设备画像选择
        ↓
默认选择：新建独立设备画像
另一个选项：使用共享设备画像
        ↓
如果新建独立画像：
仅在内存中随机生成画像 P1
        ↓
使用固定的 P1 完成整个二维码登录
        ↓
扫码成功，识别账号 A
        ↓
把 P1 保存为正式设备预设
        ↓
将账号 A 绑定到 P1
        ↓
保存二维码返回的 QuickLoginSecret
        ↓
保存账号
        ↓
直接继续后续游戏启动
```

本次暂时不需要“从已有设备画像中选择”这个选项。

设备画像选择界面应当类似：

```text
选择本次二维码登录使用的设备信息

● 新建独立设备画像
○ 使用共享设备画像

[继续] [取消]
```

默认选中“新建独立设备画像”。

# 四、核心行为要求

## 1. 扫码前生成独立画像

用户选择“新建独立设备画像”后，立即在内存中调用现有的匿名画像生成逻辑，例如：

```csharp
var generatedUtcTicks = DateTimeOffset.UtcNow.UtcTicks;
var snapshot = FakeMachineInfo.CreateSnapshot();
```

生成内容包括：

* 随机 `HostName`
* 随机 `MacAddress`
* 派生的 `DeviceId`
* 由 MAC 派生的 CASCID

注意：CASCID 可以继续由请求层按照 MAC 计算，不一定需要成为 `DeviceProfileSnapshot` 的字段。

## 2. 扫码成功前不要落盘

临时画像 P1 在扫码成功前只能存在于当前登录工作流的内存中。

在以下情况下不得创建正式设备预设：

* 用户在画像选择界面取消；
* 用户取消二维码登录；
* 二维码超时后退出；
* 扫码失败；
* 登录接口返回错误；
* 验证码或风险验证失败。

因此扫码失败或取消时，只需要丢弃内存对象，不需要删除磁盘文件。

## 3. 同一次二维码会话必须固定使用同一份快照

整个二维码登录会话必须持有一份不可变的 `DeviceProfileSnapshot`。

从以下所有阶段都必须使用同一份实例或同一份不可变数据：

```text
获取 GUID
生成二维码
二维码轮询
二维码过期后刷新
扫码确认
获取 TGT
获取 QuickLoginSecret
获取后续登录结果
```

禁止在扫码过程中再次调用：

```csharp
accountManager.ResolveDeviceProfile(...)
FakeMachineInfo.CreateSnapshot()
```

来替换画像。

需要避免：

```text
生成二维码时使用 P1
二维码轮询时重新读取配置，变成 P2
```

建议引入一个明确的准备结果对象，名称可以自行决定，例如：

```csharp
internal sealed record PendingQrDeviceProfile(
    DeviceProfileSnapshot Snapshot,
    bool UseShared,
    long GeneratedUtcTicks
);
```

不强制使用这个准确名称和结构，但必须清楚表达：

* 当前固定快照；
* 是共享还是新建独立；
* 新画像的真实生成时间；
* 是否尚未持久化。

## 4. 二维码过期刷新继续使用 P1

如果二维码过期，但仍属于同一次登录操作：

```text
二维码 1：P1
二维码 2：P1
二维码 3：P1
```

不能变成：

```text
二维码 1：P1
二维码 2：P2
二维码 3：P3
```

只有用户彻底退出本次登录，再重新点击二维码登录时，才可以重新生成画像。

# 五、扫码成功后的绑定逻辑

扫码成功后，可以通过登录结果知道真实账号，例如：

* `InputUserID`
* `SndaID`
* 账号类型
* `QuickLoginSecret`

## 选择“新建独立设备画像”

扫码成功后：

1. 使用本次固定快照 P1 创建正式设备预设。
2. 将账号绑定到这个新预设。
3. 设置：

   * `DeviceProfileDynamicEnabled = true`
   * `DeviceProfilePresetId = 新预设 ID`
   * `DeviceProfileLastGeneratedUtcTicks = P1 实际生成时间`
4. 保持或设置合理的：

   * `IsDeviceProfileRotation`
   * `DeviceProfileRotationDays`
5. 保存二维码返回的 `QuickLoginSecret`。
6. 让账号以后可以正常使用 QuickLogin。

不能把 `LastGeneratedUtcTicks` 设置成共享预设的旧时间，也不能在保存时重新取一个与实际生成时间无关的时间。

## 选择“使用共享设备画像”

从二维码生成开始就使用共享画像。

扫码成功后，账号保持共享模式：

```text
DeviceProfileDynamicEnabled = false
```

不要在扫码后再切换画像或二次登录。

# 六、扫出已有账号时的行为

二维码生成前不知道最终扫出哪个账号。

如果扫码成功后发现账号 A 已经存在：

```text
账号 A 原来绑定 P0
本次二维码登录使用 P1
```

那么应当：

```text
将账号 A 更新为绑定 P1
保存本次新的 QuickLoginSecret
以后账号 A 使用 P1 登录
```

这是用户本次二维码登录时主动选择新建画像的结果，不需要再次询问。

但是更新已有账号时必须保留所有与本次操作无关的数据，包括但不限于：

* 用户自定义显示名；
* 排序位置；
* 大区设置；
* 其他仍然有效的账号配置；
* 不应无意清空的已保存凭据；
* 与设备画像无关的字段。

请特别检查当前 `SaveAccountAsync()` 和 `AccountManager.AddAccount()` 的字段覆盖行为，避免二维码重新绑定设备画像时意外清空已有密码、备注或其他配置。

旧预设 P0 第一版可以先保留，不要求立即清理。不要因为删除旧预设而影响仍然引用它的其他账号或共享预设。

# 七、关于 QuickLogin：必须正确理解

需要删除的是：

```text
首次二维码扫码成功后，
为了把共享画像 S 切换为独立画像 P1，
立即执行的那一次重复 QuickLogin。
```

也就是当前 `LoginWorkflowService.ExecuteAsync()` 中类似下面条件触发的重登：

```csharp
if (首次二维码登录
    && 登录成功
    && 账号启用了独立画像)
{
    LoginAsync(
        LoginType.QuickLogin,
        QuickLoginSecret,
        新设备画像);
}
```

修改后第一次二维码登录从一开始就已经使用 P1，因此这次立即重登是多余的，应当删除。

但是绝对不能删除以下能力：

```text
账号 A 第一次二维码登录成功
→ 保存 QuickLoginSecret
→ 下次用户选择账号 A
→ 使用保存的 QuickLoginSecret + P1 正常 QuickLogin
```

也就是说：

```text
删除：扫码成功后的立即重复 QuickLogin
保留：未来启动账号时的正常 QuickLogin
保留：游戏 session 需要刷新时使用的 QuickLogin 回调
```

请检查当前 `LoginQuickLoginEnabled`、`ResolvedLoginState.QuickLoginEnabled`、`QuickLoginEnabled` 和 `SaveAccountAsync()` 之间的关系。

确保二维码登录可以取得并保存 `QuickLoginSecret`，并确保账号下次不需要再次扫码。

不要因为删除二次登录而导致：

* `QuickLoginSecret` 没有保存；
* `QuickLoginEnabled` 被错误设置为 false；
* `RefreshGameSessionIdByQuickLoginFunc` 失效；
* 后续 DC Travel/session 刷新逻辑失效。

# 八、UI 和 STA 线程要求

所有 WPF 对话框和控件必须在主 UI Dispatcher 上创建和访问。

当前已有异常说明以下方法可能在后台线程执行：

* `PromptNewAccountDeviceProfileChoice`
* `ConfigureTemporaryAccountDeviceProfile`
* 其他由登录流程调用的 WPF 对话框

请统一审查 `MainWindowLoginInteraction`。

调用 UI 时应使用现有主窗口的：

```csharp
window.Dispatcher.Invoke(...)
```

或合适的异步 Dispatcher API。

不要创建额外 STA 线程，也不要让设备画像窗口拥有自己的独立 Dispatcher。

新的二维码画像选择应在二维码网络请求开始前显示，并默认选中“新建独立设备画像”。

原有非二维码登录流程如果仍然会使用 `ConfigureTemporaryAccountDeviceProfile`，也必须顺手修复其 Dispatcher 问题。

# 九、持久化和失败处理

设备预设存储在 JSON，账号和凭据使用另一套存储，因此无法直接假设它们处于同一个 SQLite 事务。

不要声称实现了真正的跨存储原子事务，除非确实重构了存储方式。

第一版采用以下安全顺序：

1. 扫码成功前不持久化临时画像。
2. 先完成可能失败的凭据加密和账号数据准备。
3. 创建正式设备预设。
4. 绑定并保存账号。
5. 如果创建预设后账号保存失败：

   * 尝试删除本次刚创建且尚未被任何账号引用的预设；
   * 不得删除共享预设；
   * 不得删除已被其他账号引用的预设；
   * 保留清晰错误日志。

如果现有 `AccountManager` API 不方便安全完成该操作，可以增加一个范围有限的协调方法，但不要重构整个账号存储系统。

随机生成出的画像理论上可能与已有画像完全相同，但概率极低。本次可以为每次成功的独立二维码登录显式创建一个新的预设，不必为这个极低概率设计复杂流程。

# 十、轮换时间

独立画像 P1 的轮换时间必须从它真正生成的时刻计算：

```csharp
DeviceProfileLastGeneratedUtcTicks = pendingProfile.GeneratedUtcTicks;
```

不能继承：

* 共享画像生成时间；
* 旧账号画像生成时间；
* 账号第一次加入数据库的时间。

七天轮换逻辑本身可以保留。

本次修改不需要改变轮换算法，只需要确保首次绑定时间正确。

# 十一、尽量保持其他流程不变

不要无关修改以下行为：

* 静态账号密码登录；
* 一键登录；
* WeGame 登录；
* 已保存账号的普通 QuickLogin；
* 游戏 session ticket 获取；
* DC Travel/session 刷新；
* 补丁与游戏启动逻辑；
* Dalamud 启动逻辑。

如果为了复用代码必须调整公共类型，请控制影响范围并解释原因。

# 十二、日志要求

增加必要的结构化日志，用于验证流程：

```text
二维码登录选择共享画像
二维码登录生成临时独立画像
二维码登录固定画像快照
扫码成功后创建正式预设
新账号绑定预设
已有账号重新绑定预设
取消登录并丢弃临时画像
账号保存失败并清理孤立预设
```

日志不得包含：

* 完整 `QuickLoginSecret`
* TGT
* SessionID
* 完整 DeviceId
* 完整 MAC 地址
* 账号密码

如需识别画像，只记录：

* 是否共享；
* 预设 ID；
* DeviceId 的短哈希或前几位；
* 不含敏感信息的状态。

# 十三、验收场景

修改完成后，至少验证以下场景：

## 场景 1：新账号 + 新建独立画像

```text
点击二维码登录
→ 默认新建独立画像 P1
→ 使用 P1 生成并轮询二维码
→ 扫码成功得到账号 A
→ 只发生一次二维码认证
→ 创建正式预设 P1
→ A 绑定 P1
→ 保存 QuickLoginSecret
```

下次登录账号 A：

```text
读取 P1
→ 使用已保存 QuickLoginSecret 正常 QuickLogin
→ 不再扫码
```

## 场景 2：新账号 + 使用共享画像

```text
二维码全过程使用共享画像
→ 扫码成功
→ 账号保存为共享模式
→ 不发生二次 QuickLogin
```

## 场景 3：已有账号重新扫码并选择新画像

```text
A 原来绑定 P0
→ 本次二维码使用 P1
→ 扫码成功仍然识别为 A
→ A 更新为绑定 P1
→ 新 QuickLoginSecret 被保存
→ 备注、排序及其他无关配置保留
```

## 场景 4：用户在生成二维码前取消

```text
不发起二维码登录
不创建预设
不修改账号
```

## 场景 5：二维码登录取消或失败

```text
临时 P1 仅存在内存
不创建正式预设
不修改账号绑定
```

## 场景 6：二维码过期后刷新

```text
二维码 1 使用 P1
二维码 2 仍然使用 P1
```

## 场景 7：持久化失败

```text
不得留下账号引用不存在预设
尽力清理本次创建但无人引用的预设
不得影响共享预设或其他账号
```

## 场景 8：STA 线程

设备画像选择和其他登录对话框不再出现：

```text
调用线程必须为 STA
```

## 场景 9：其他登录方式

静态登录、一键登录、WeGame 和已保存账号 QuickLogin 行为不变。
